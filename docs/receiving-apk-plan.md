# แผน: แอป Android รับสินค้า + อ่านบิล (Receiving APK)

วันที่ 14 ต.ค. 2569 · สถานะ: ร่างแผน รอเจ้าของตัดสินใจข้อ 0

## เป้าหมาย

ให้คนรับของหน้าร้านทำงานจบในแอปเดียวตอนของมาส่ง:
ถ่ายบิล → ระบบอ่านรายการ → เทียบกับใบสั่ง → แก้จำนวนที่รับจริง → เซ็นรับ → ส่ง

ข้อมูลที่ได้ต้องใช้ต่อได้ทันทีโดยไม่พิมพ์ซ้ำ: ยอดรับของ (ต้นทุนตามเดือนรับของ), หนี้ค้างจ่ายซัพพลายเออร์, คลังสินค้า และหลักฐานสำหรับจ่ายเงินรอบวันที่ 5/20

## สิ่งที่มีอยู่แล้ว (สำรวจโค้ด 14 ต.ค.)

| ส่วน | มีแล้ว | ยังขาด |
|---|---|---|
| ระบบสั่งของ (MySQL, Express, JWT) | `order_items` มี `received_quantity`, `actual_price`, `received_by_user_id`, `received_at`; `PUT /api/orders/receiving`; รูปบิล `receiving_bill_photos` (BLOB); หน้า `ReceiveOrders.jsx`; ใบสั่งซื้อ `purchase_orders` + `purchase_order_receipts` | ไม่มี OCR, รับของไม่บันทึกราคา, ไม่มีลายเซ็น, ไม่มีหัวเอกสารบิล (เลขบิล/ยอดรวม/VAT), ไม่มีแอปมือถือ (มีแค่ web manifest) |
| LINE Bill (SQLite, OpenAI vision) | อ่านบิลได้: ร้าน, เลขที่, วันที่, ยอดรวม, สลิป; เรียนรู้หมวดจากตัวอย่าง | ไม่อ่านรายการสินค้าทีละบรรทัด, ไม่มี VAT, รับรูปได้ทาง LINE webhook เท่านั้น, ไม่เชื่อมกับระบบสั่งของ |
| Cashflow P&L | ต้นทุนมาจากยอดจ่ายบิล LINE | ไม่มีต้นทุนตามเดือนรับของ |

## 0. เรื่องที่ต้องตัดสินก่อนเริ่ม

1. **ใช้แทน LINE หรือคู่กัน:** แนะนำช่วงทดลองให้แอปส่งรูปเข้า LINE Bill ด้วย (ต้องเพิ่ม API รับรูปใน LBC) เพื่อไม่ให้ขั้นตอนจ่ายเงินเดิมสะดุด
2. **ใครรับของ:** หัวหน้ากะแต่ละสาขา/แผนก ใช้บัญชีเดิมของระบบสั่งของ
3. **เครื่อง:** มือถือ Android ของร้านหรือของพนักงาน (APK ติดตั้งเอง ไม่ขึ้น Play Store)
4. **ซื้อตลาดสด/ไม่มีบิล:** ใช้ "ใบรับของ" ในแอปแทนบิล (กรอกเอง + ถ่ายรูปของ)
5. **ราคา:** เก็บราคาต่อหน่วยตอนรับของเลย (ใช้ตั้งหนี้และต้นทุน)

## 1. สถาปัตยกรรม

```
แอป Android (Capacitor + React)
  │  JWT ของระบบสั่งของ · กล้อง · ลายเซ็น · คิวส่งตอนออฟไลน์
  ▼
Market order server (Express/MySQL)  ← เพิ่มโมดูล receiving-documents
  ├─ POST รูปบิล → งานอ่านบิล (vision model ฝั่ง server, คีย์อยู่ server เท่านั้น)
  ├─ จับคู่บรรทัดบิล → สินค้า/ใบสั่ง (ตารางชื่อเรียกของซัพพลายเออร์)
  ├─ ยืนยันรับ → order_items.received_* + inventory_transactions(receive)
  ├─ ตั้งหนี้ซัพพลายเออร์ (ตามเดือนรับของ)
  └─ (เลือกได้) ส่งรูป + ข้อมูลเข้า LINE Bill
            ▼
Cashflow P&L อ่านยอดรับของรายเดือน → ต้นทุนตามเกณฑ์คงค้าง
```

**ทำไม Capacitor:** ใช้ React เดิมของระบบสั่งของได้ แชร์โค้ดหน้า `ReceiveOrders` ได้บางส่วน ได้กล้องจริง ไฟล์ออฟไลน์ และสร้าง APK ได้โดยไม่ต้องเขียน Kotlin

## 2. ฐานข้อมูล (เพิ่มแบบ additive ใน MySQL ของระบบสั่งของ)

- `receiving_documents`: id, branch_id, department_id, supplier_master_id/product_group_id, delivery_date, doc_ref, doc_date, subtotal, vat, total, status (`draft|confirmed|void`), receiver_user_id, receiver_signature (รูป), courier_name, courier_signature, ocr_status, ocr_model, ocr_confidence, lbc_capture_id, created/confirmed time, audit
- `receiving_document_lines`: document_id, line_no, bill_text, product_id, order_item_id, quantity_billed, quantity_received, unit, unit_price, amount, match_confidence, note
- `receiving_document_images`: document_id, page_no, เก็บไฟล์ (เริ่มจาก BLOB แบบ `receiving_bill_photos` เดิม แล้วค่อยย้ายไป object storage), sha256
- `supplier_product_aliases`: supplier + ข้อความในบิล → product_id + ตัวคูณหน่วย (เช่น "ลัง" = 12 ชิ้น) เรียนรู้จากการยืนยันของคน

## 3. การอ่านบิล

- **Schema ใหม่ระดับบรรทัด:** ร้าน, เลขที่, วันที่, รายการ (ชื่อ, จำนวน, หน่วย, ราคาต่อหน่วย, จำนวนเงิน), ส่วนลด, VAT, ยอดรวม, ความมั่นใจต่อช่อง
- **โมเดล:** เริ่มจาก provider เดียวกับ LBC (OpenAI vision) เพื่อใช้คีย์และระบบเดิม แล้ววัดผลเทียบกับ Claude/Gemini บนบิลจริงก่อนเลือกตัวถาวร
- **ชุดทดสอบ:** บิลจริงเดือน ส.ค.–ก.ย. 100–200 ใบ (บนสำเนา SSD) วัด 3 อย่าง: ยอดรวมตรง, จำนวนบรรทัดตรง, จับคู่สินค้าถูก เป้าหมายยอดรวมตรง ≥ 98% และกำหนดว่าถ้าความมั่นใจต่ำ ต้องให้คนตรวจทุกบรรทัด
- **กันผิด:** ผลรวมบรรทัดต้องเท่ายอดรวมบิล ไม่งั้นเตือน; ราคาต่างจากราคาล่าสุดเกิน X% เตือน; บิลซ้ำ (ร้าน+เลขที่+ยอด) เตือน
- **ต้นทุน:** ประมาณ 1–3 บาทต่อบิลตามขนาดรูปและโมเดล (ต้องวัดจริงในข้อ 3)

## 4. หน้าแอป

1. เข้าสู่ระบบ (บัญชีเดิม) → เลือกสาขา/แผนก
2. **ของที่ควรมาวันนี้:** รายการจากใบสั่ง จัดกลุ่มตามซัพพลายเออร์
3. **ถ่ายบิล:** หลายหน้าได้, ครอปอัตโนมัติ, ย่อรูปก่อนส่ง
4. **ตรวจรายการ:** ระบบเติมจำนวน/ราคาจากบิล จับคู่กับใบสั่ง แสดงสีเตือน (ขาด, เกิน, ราคาเปลี่ยน, หาสินค้าไม่เจอ) แก้จำนวนที่รับจริงได้
5. **เซ็นรับ:** ผู้รับ + คนส่งของ (ถ้ามี) เซ็นบนจอ
6. **ส่ง:** ถ้าไม่มีเน็ต เก็บในคิวแล้วส่งเองเมื่อออนไลน์
7. **ประวัติ:** บิลที่ส่งแล้ว สถานะ และบิลที่ระบบขอให้ตรวจ

## 6. กติกาที่ต้องทำตาม

- แตก branch จาก `production-base` ของแต่ละระบบ ไม่ใช้ checkout หลัก (มีงานค้างของหลายแชต และไม่ตรง Production)
- ข้อมูลทดสอบ/รูปบิล/รายงาน/build ไว้บน SSD ตาม `SSD_POLICY.md`
- ก่อนเพิ่มตารางบน Production ต้องสำรองฐานข้อมูลแบบสมบูรณ์ลง SSD
- คีย์ AI อยู่ฝั่ง server เท่านั้น ไม่ฝังใน APK; กุญแจเซ็น APK เก็บนอก repo
- ทุกการแก้ยอด/ยืนยันรับมี audit; ไม่ลบบิลเดิม

### จุดหยุดอัตโนมัติ (ไม่ทำต่อเอง)
- SSD หลุด / พื้นที่เหลือน้อยกว่า 5 GiB
- เทสต์เดิมของระบบสั่งของพัง (แปลว่างานใหม่กระทบของเดิม)

- ทุกอย่างที่แตะ Production (ฐานข้อมูลจริง, deploy, LINE Bill จริง)

### หลังคืนนั้น (ต้องอนุมัติ)
สำรองฐานข้อมูลระบบสั่งของ → deploy server (ตารางใหม่ additive) → แจก APK ให้ 1 สาขาใช้คู่กับ LINE 2 สัปดาห์ (P4) → เชื่อม Cashflow (P5)

## 7. ความเสี่ยง

- บิลเขียนมือ/ตลาดสด อ่านพลาดสูง → ให้คนยืนยันทุกบรรทัดเมื่อความมั่นใจต่ำ และใช้ใบรับของในแอปแทน
- พนักงานไม่ใช้ → ทดลองสาขาเดียวก่อน เก็บเวลาที่ใช้ต่อบิล ต้องไม่ช้ากว่าการถ่ายส่ง LINE
- ยอดคลังในระบบสั่งของยังเพี้ยน → ช่วงแรกใช้ยอดรับของเป็นต้นทุน ยังไม่อ้างยอดคงเหลือ
